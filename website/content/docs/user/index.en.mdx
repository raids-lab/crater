## Platform Introduction

Crater is a platform developed by The Crater Project Team, RAIDS-Lab. It is specifically designed for cluster management, providing users with an efficient and convenient solution for managing cluster resources. It can uniformly schedule and manage computing resources, storage resources, and more within the cluster, ensuring stable operation of the cluster and optimal utilization of resources.

### Intuitive Interface Design

Crater provides a simple and user-friendly interface, allowing users to easily complete various cluster management tasks through a graphical operation interface. For example, the resource dashboard can display real-time usage of cluster resources, including CPU utilization, memory usage, storage capacity, and other metrics.

The job management interface presents currently running jobs, job queues, and job history records, making it convenient for users to check task statuses and perform operations at any time.

![jobshow](./assets/jobshow.webp)

### Efficient Resource Scheduling

The platform uses intelligent resource scheduling algorithms to automatically assign the optimal resources to jobs based on factors such as job priority and resource requirements. For example, when multiple jobs simultaneously request resources, Crater can quickly analyze and allocate resources to the most urgent and critical tasks, improving overall execution efficiency.

### Monitoring Functionality

Detailed monitoring data and log records provide users with the basis to deeply understand the operation status of the cluster, facilitating fault diagnosis and performance optimization.

## Browsing Paginated Lists

### Templates, datasets, shared files, models, and images

1. Open the relevant list and narrow the results with its search and filter controls. Paginated queries search, filter, and sort before returning the requested page; search is not limited to records on the current page.
2. Use the page numbers, previous/next controls, and page-size selector below the list. The total counts records you can access under the current filters.
3. On template, dataset, shared-file, and model pages, changing the search, owner filter, sort, or page size returns to page one. Existing permissions still govern template updates and deletion.

The model overview groups models by organization. Open an organization to view its models. Model pages retain local search, filtering, and pagination; the overview total counts matching organizations.

Account-member tables load one page at a time and support username search, sorting, and role and access-mode filters. Dataset shared-user tables still load the complete list and search, sort, and paginate locally. When adding members or sharing a dataset, the selector still shows the complete list of eligible users.

Template, dataset, and shared-file lists preserve the requested page when a read fails and provide a Retry control. Select Retry to try again; missing data or an unavailable total after a failure does not mean a successful query found zero records. If deletion leaves the current page beyond the latest results, a successful reload moves to the last valid page.

### Loading ordinary job Pods in batches

The Basic Information tab for an ordinary Volcano job loads a Pod snapshot in batches. Load More appends the next batch; after a successful read, no Load More button means the current snapshot is complete. Search, filters, and sorting apply only to loaded Pods. Pod state can change; Refresh Snapshot starts a new read. This list has no numbered pages or database-style total. EMIAS jobs continue using their existing detail and Pod read APIs; this pagination change does not add an EMIAS snapshot endpoint.

The administrator's node-management page also loads snapshots in batches. File directories, account members, and dataset-sharing relation tables do not use this snapshot pagination.
