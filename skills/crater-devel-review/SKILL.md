# Crater 开发 · Review

**开始前先应用 [`crater-devel-shared`](../crater-devel-shared/SKILL.md)。** 本 Skill 用于帮助开发者在提交或 PR 前纵览 monorepo 变更、发现问题、生成 PR review 评论草稿并撰写 PR 描述。开发规范的完整权威来源是各级 `CONTRIBUTING`；`.github/instructions/*` 是引用 CONTRIBUTING 的审查 MUST/SHOULD 清单。GitHub Copilot code review 阶段的行内 / 总览评论格式由 `.github/copilot-instructions.md` 负责，本 Skill 不强制遵循那套输出形态。

## 审查方式与顺序

默认以静态审查为主，适用于已有 PR 和提 PR 前的本地变更。阅读源码、契约、测试及已有 CI 证据，不把启动服务、访问真实集群或执行完整测试套件作为审查前提。用户要求纯静态审查时不运行被审查代码；需要动态验证才能确定的结论，明确限制并给出验证建议。审查本身不授权修改代码、rebase、提交或发布评论。

按“范围 → 目标 → 整体逻辑 → 细节与异常 → 结论”推进；下方领域清单用于补漏，不能代替理解实现。

1. **先核对变更范围**：确认 base / head 和审查快照，读取完整文件清单、增删 / 重命名与 diff 概览，再深入具体代码。PR 以相对目标分支的合并差异为准；提 PR 前还要区分分支提交、暂存、未暂存及拟纳入的未跟踪文件，避免漏审或把无关本地文件算进 PR。结合任务意图，检查无关改动、调试截图、日志、临时配置 / 产物、意外删除及大面积格式变化；初步列出可能遗漏的调用方、测试、文档、翻译、生成文件或配置联动，后续沿逻辑验证，不能仅凭文件未变就断言遗漏。按下方“变更范围与孤立资源”核实资源用途。
2. **建立预期行为**：先读需求、Issue、PR 描述和相关契约，明确要解决谁的什么问题、主要场景、输入输出、权限边界、成功条件和不应改变的行为。PR 描述是待核实的意图，不是实现正确的证据；需求不明时区分已知事实与推断，提出会影响判断的具体问题，不自行扩大功能范围。
3. **还原实际实现并对照目标**：从入口沿调用链、数据流和状态变化阅读必要的上下文，包括未修改的调用方与被调用方。按主要场景推演“代码实际上会做什么”，检查整个流程是否闭合、顺序和状态是否合理、跨组件契约是否一致，以及是否遗漏入口或破坏已有路径；不要只看修改行或把测试通过等同于目标达成。同时判断代码的模块 / 文件归属、职责和依赖方向是否自然，是否把业务特例塞进公共层或重复已有机制；指出具体维护或行为影响，不因个人目录偏好要求重构。

   **结合 Crater 的场景与环境判断合理性**：从相关代码、架构文档、部署配置和工作负载中识别会改变设计取舍的约束，不默认单用户、单机或本地磁盘环境。例如，多租户下要考虑隔离、共享资源竞争及跨租户影响；分布式存储下要考虑大量小文件读写和元数据操作可能带来的成本。以上只是启发，Agent 应按本次改动自行补充相关因素，并结合实际访问模式、规模和已有机制评估正确性、性能与故障影响，而非套用固定场景清单或泛化最佳实践。环境事实不明时标明假设和需确认的信息，不编造部署规模、性能瓶颈或据此强推优化。

4. **再检查细节和异常路径**：围绕实际调用链选择适用场景，重点看常见输入错误、空 / 缺失数据、权限失败、依赖不可用或超时、部分成功、重试 / 重复请求、并发和中断后的状态与资源清理。优先关注越权、数据丢失 / 不一致、重复副作用、大范围不可用和显著资源消耗等后果；低频但高影响且有可信触发路径的风险也应说明，不穷举脱离项目场景的假想故障。检查测试是否验证预期行为和关键失败分支，而不只是复述当前实现；快照也不能替代逻辑判断。
5. **以证据收敛结论**：对候选问题复查调用方约束、已有校验 / 回退与测试，排除误报，并区分本次引入、加剧或暴露的问题与无关历史问题。每条发现说明“触发条件 → 实际行为 → 预期差异 / 影响”，给出代表位置和修复或验证方向。优先整体逻辑和实际风险，再报告细节；不要求代码绝对完美，不为风格偏好、低收益抽象或没有可信场景的防御性代码制造阻断。

### 说明实际检查与验证依据

每条问题发现、重要风险或实质性 review 意见都要简要说明实际做过的检查，以及这些证据能支持到哪一步；不能只在总览写“静态审查”，却让具体评论看起来像已实测复现。可用一句“验证情况”自然融入正文，不要求统一长模板：

- **静态检查**：说明核对了哪些关键调用链、条件、契约或测试源码，并明确“未实测复现”。阅读测试不等于运行测试，代码推演也不等于观察到运行结果；静态证据充分时仍可明确指出缺陷。
- **执行验证**：若实际运行了测试、最小复现或命令，说明场景 / 命令、环境边界和观察结果。引用已有 CI、日志或开发者提供的结果时标明来源，不冒充本次亲自执行，也不把无关测试通过写成该问题已验证。
- **外部依据**：若查阅了 Ceph 等依赖的文档或实现源码，给出相关链接或源码位置、已知版本 / commit，并说明它确认了哪一项行为。区分文档约定、源码实现与实测结果；未核实与实际部署版本是否一致时注明限制。

按风险和可用条件选择验证深度，不强制每条意见都做实测或追踪外部源码。没有做的检查如实说明；尚缺证据的关键环节与下一步验证建议分开列出，不写成已完成的验证。

## 分级与语气

- 评价、总结、统计与描述一律用**简体中文**。
- 每条**代码审查发现**标注等级：
  - **【核心规范】**（MUST）：违反视为阻断性问题。
  - **【优化建议】**（SHOULD）：参考改进方向。
- 分级标签只用于审查差异中可合理锚定到变更行的代码、文档、配置、测试或仓库文件问题（二进制资源按文件定位）。人工验证、截图证据、CI、PR 描述、关联 Issue、分支 / 提交状态等属于 PR 整体状态，不使用上述标签，也不计入代码审查发现数量。
- 已确认的功能正确性、安全或重大可靠性缺陷按实际影响判断是否阻断，不能因清单没有逐字列出就忽略。证据不足的疑点不写成确定缺陷；重要但尚待确认、暂不修复或已接受的风险仍须告知开发者，按下方“重要风险与待确认事项”报告。已确认的阻断缺陷不会仅因暂不修复就自动降级。
- 作为资深导师：礼貌、专业、有建设性；指出问题同时肯定亮点。若某规范在当前场景反而损害质量，明确指出并建议修订对应指令文档。

## 核心规范检查要点（跨目录速查）

- **安全**：无硬编码密钥/Token/密码/内网 IP；DAO 与存储层无 SQL 字符串拼接。
- **后端**：管理员接口入 `Admin` 路由、用户接口入 `Protected` 路由；外部 API 变更同步 `swag`；HTTP 状态码符合 RESTful；错误信息为清晰英文。
- **CLI / 后端 API 版本**：只有 CLI 所用 API 契约本身变化时，才在后端与 CLI 同步提升共享 `APIVersion`；CLI 开始依赖契约中已有能力时当前版本不变，双方最低支持版本只在无回退路径且确实不再兼容旧版对方时独立提升至该能力首次出现的版本。两项结论都必须在 PR 中说明。检查诊断 Header 未被用于鉴权、请求拦截或响应分流；普通业务命令不得自动握手，只有 `crater compatibility` 显式检查，版本不兼容或握手接口 404 时返回稳定错误 `ERR_API_VERSION_MISMATCH`。接口明确报告的 `0` 必须作为前契约旧版本参与比较并输出完整不兼容诊断，不能与字段缺失混为非法响应；404 的 `0` 占位仍显示未知。人类提示须分段列出失败条件、双方当前和最低支持版本以及可继续使用的风险，不得优先把业务错误归因于版本问题；应先提示排查操作报错、输入、配置、认证、网络、平台状态和 CLI 缺陷，排除这些原因后才把调整 CLI 作为最后手段。CLI 低于后端要求时升级，后端低于 CLI 要求或接口 404 时降级，两项限制同时不满足时说明方向冲突并提示向管理员确认。404 特殊映射不得影响其他命令，并须保留原始 HTTP context。
- **作业模板**：作业配置字段、模板持久化结构、模板序列化或 clone / template source 变更须检查是否提升对应前端 `MetadataForm*` version；提升版本时必须有“上一版本 -> 当前版本”的迁移函数并接入模板迁移注册表，旧版本通过链式迁移升级，不支持的更早版本要明确报错。新增或修改作业模板加载 / 解析入口时，必须复用统一模板迁移逻辑，不要手写局部兼容，也不要把任意 JSON 导入误接入作业模板迁移。
- **前端**：无硬编码文本（接入 i18n）；翻译 key 使用英文语义 key 并放入合适 domain，不得新增中文 key；新增 / 修改可翻译文案须同步所有语言 `translation.json`，保证翻译准确和专有名词一致；身份判断用 `useIsAdmin()`；非幂等操作执行前须有确认弹出框，说明操作对象和后果；改动 `ui-custom/` 等高复用组件须评估影响范围与兼容性（审查时列为核心规范，要求开发者确认）；不易理解的输入 / 配置项须提供帮助图标与 hover tooltip。
- **Chart**：`values.yaml` / 模板 / 依赖 / 配置项行为或默认值变更须提升 `charts/crater/Chart.yaml` 的 `version` 与 `appVersion`，二者必须保持完全相同的值，并同步 `charts/crater/README.md`；values-only 可 patch，前后端 API 变化影响应用契约须 minor，不主动 major；版本发布变化须提醒创建 GitHub tag；新增项含英文注释。
- **文档**：`website/` 应面向平台用户（集群用户与集群管理员）承载部署、使用、管理、排障等产品文档；`docs/` 和仓库各级 `.md` 默认面向开发者 / 贡献者。归档须正确；术语准确（Account=调度队列）；`website/` 部署命令无硬编码 Chart 版本，命令附近用 `<CraterChartVersionNotice />`，代码块内用 `<chart-version>`，Chart 配置页用 `<ChartBadge />`。
- **变更范围与孤立资源**：在审查开始时按上方流程核对范围，在理解调用链后复核遗漏和文件职责。对图片、日志、调试文件等资源，检查代码、文档、测试、配置及构建中的实际用途，考虑约定式或动态引用；不要仅因扩展名或搜索不到静态引用就认定其无用。仅供 PR 描述或评论使用的截图不得提交到仓库，应按文件路径作为 **【核心规范】** 问题报告并要求改用 PR 附件。其它无关临时文件按用途、泄密或发布影响说明问题；无法确认时列出证据并要求说明。二进制文件可按路径定位，不得编造行号，也不得因无可读 diff 而跳过。
- **开发 Skill 版本**：若 `skills/crater-devel-*` 中任一 Skill 目录相对目标分支发生变化，核对该 Skill 的 `version` 是否高于目标分支，并按该目录最终累计范围判断 patch / minor / major 是否恰当；references、scripts、assets 等随 Skill 分发的文件也计入。版本代表整个分支 / PR 的一次变更集，不要求因后续编辑或多个 commit 重复提升；若范围由 patch 扩大为 minor，应直接从目标分支基线进位。缺少提升、版本不高于 rebase 后的新基线或级别明显不当，作为可锚定到版本行或触发义务的 Skill 变更行的 **【核心规范】** 问题报告。
- **联动**：功能上线同步 `website/` 文档；配置结构变更同步 `charts/`。
- **发布准备与公告**：按根 `CONTRIBUTING.md` 的发布与 Release 文案章节、前端 What's New 和 CLI 发布维护章节核对版本、事实、翻译及发布状态措辞。diff 中的实际错误可作为行内发现；tag 目标、发布产物、npm 审批或安装验证证据不足只在 PR 整体状态报告，不混入代码发现。

## PR 整体状态检查（不作为行内问题）

以下信息必须检查并在 review 总览中报告，但它们描述的是 PR 的验证证据和协作流程，不是针对某一行代码的修改，因此不得放入 **【核心规范】** / **【优化建议】** 问题清单，也不得伪装成行内评论：

- **CI 与自动验证**：说明 workflow、构建、测试、lint 等已执行、失败、未执行或无法确认的状态。后端 / CLI 构建或测试应先确认本地 `go version` 符合对应 `go.mod` / CONTRIBUTING；后端 `make run` 缺少真实配置、凭据或集群访问时说明限制，不要求 Agent 反复尝试。
- **开发者人工验证**：说明已有验证覆盖了哪些页面、角色、命令、场景或文档，以及仍缺哪些关键场景；文档改动必须由开发者人工阅读检查。人工验证缺失或不完整可影响合并建议，但只作为 PR 整体待补充项报告。
- **截图证据**：保留根 CONTRIBUTING 的截图要求：前端 / UI 改动应在 PR 描述或评论中提供实际界面截图，无有意义的可见变化或无法截图时说明原因；其他改动按审查价值推荐实际执行截图，例如 CLI 输出。缺少截图、覆盖不完整、未说明原因或证据归属不清时，只在总览简短提醒，不使用【核心规范】或【优化建议】标签，不生成行内评论、不计入代码问题数量，也不单独据此建议阻止合并。Agent 操作真实环境后的截图有效但属于 AI 检查；AI 生成图、模拟图或设计稿不作为验证证据，在总览提醒替换。截图暴露的实际代码缺陷，或仅供 PR 使用的图片被提交到仓库，仍按独立的代码或修改范围问题检查。
- **PR 与 Git 状态**：检查 PR 描述、关联 Issue、head / base、领先 / 落后提交数、分支名、commit message 和最终文件清单；缺失或不符合约定时作为 PR 整体待处理项报告。按根 `CONTRIBUTING.md` 核对分支前缀表示改动类型，而非 `codex/`、`zhangsan/` 等工具或作者；不符合时在总览简短提示并建议合适名称，不列为【核心规范】或【优化建议】，也不生成行内评论。任务分支落后目标 base 时提示 rebase 或取得维护者明确接受。

PR 整体状态建议使用“通过 / 待补充 / 不适用 / 无法确认”等状态，并与代码发现数量分开统计。若流程证据暴露出实际代码缺陷，只有在能指出由 diff 引入的问题并锚定到代表变更行时，才另行生成代码审查发现。例如“缺少某页面截图”属于 PR 整体项，而截图证明某个页面渲染错误时，可把渲染错误锚定到引入它的代码行。

## 版本与部署影响（每次 review 强制输出）

每次 review 都必须基于目标分支 diff 检查以下两项，不要只检查版本文件有没有改：

- **CLI API 契约与兼容范围**：按根 `CONTRIBUTING.md` 的决策表识别 CLI 消费的接口、字段、路径、方法、类型、语义或鉴权要求变化，据此核对后端与 CLI 的 `APIVersion` 是否应同步提升；同时检查双方对已有能力的依赖及兼容回退路径，独立判断各自最低支持版本是否需要变化，不能因契约未变而跳过此项。
- **配置或 Chart 发布变化**：按 `charts/CONTRIBUTING.md` 识别配置项新增、删除、重命名、默认值 / 行为变化，以及模板、依赖或配置逻辑变化；核对 `charts/crater/Chart.yaml` 的 `version` / `appVersion` 是否按正确级别同步提升、`charts/crater/README.md` 是否同步。若前后端 API 变化同时影响 Chart 所部署应用的契约，还要检查是否需要 Chart minor 提升。

总览评论中必须单列 **“版本与部署影响”**，并始终包含以下两个条目，不得因版本未变化而省略：

- **CLI API 契约与版本**：分别报告以下结论，每项标明“已变化”“未变化”或“无法确定”及依据，不能用一个总状态代替独立判断，也不能用“无”代替结论：
  - API 契约：指出相关接口 / 字段 / 语义及代表文件，或说明未变化的依据。
  - 当前 `APIVersion`：说明是否应提升及后端与 CLI 是否同步；变化时列出旧值与新值。
  - 后端 `MinSupportedCLIAPIVersion` 与 CLI `MinSupportedBackendAPIVersion`：逐项说明变化及理由；需要提升时，根据无回退的实际依赖确认所需能力首次出现的对方 API 版本，并列出旧值与新值。契约或 `APIVersion` 不变不代表最低版本不变，反之提升 `APIVersion` 也不代表需要提升最低版本。
  例如 CLI 开始强依赖已有后端能力且没有回退时，应报告“契约与当前 `APIVersion` 未变化，CLI 最低后端版本提升”；后端最低 CLI 版本仍单独判断。契约或任一版本参数变化时，列出相关构建 / 发布 / 部署影响和人工验证，尤其说明最低版本变化带来的兼容范围变化。
- **配置 / Chart 版本**：结论必须为“已变化”“未变化”或“无法确定”。已变化时指出代表文件、配置项 / 模板 / 依赖及语义，说明 `version` / `appVersion` 的“旧值 → 新值”、提升级别、README 同步和 GitHub tag，并列出 Chart 发布、既有 values 升级、`helm lint` / `helm template`、配置是否被 Pod 正确消费等人工验证；未变化时明确说明未发现需要提升 Chart 版本的配置或发布变化、`version` / `appVersion` 保持不变，且本项没有新增的 Chart 发布与部署动作。不能用“无”代替结论。

“未变化”结论也要简述判定依据，例如已检查的 API / 配置相关 diff 范围；不要仅复述版本文件没有变化。若版本发生变化，明确指出需要重新构建、发布或部署的组件 / Chart，不要把版本号变化误写成普通内部重构。

若版本缺失、未同步、提升级别错误或相关文档未更新，同时在后续问题清单中给出 **【核心规范】** 阻断项，并锚定到触发版本义务的 API / 依赖 / 回退路径 / 配置变更行或相关版本文件变更行；“版本与部署影响”不能代替问题分级。若证据不足以确定契约、最低支持版本或配置是否需要变化，将对应条目标为“无法确定”，列出不确定点并要求开发者确认，不得静默判定为“未变化”。

## 意见内容与归属

- 完成审查后直接按下方默认格式输出，不先输出一份独立问题报告再重复生成评论。总览简述目标、实现路径、范围判断与验证边界，包含版本与部署影响，并整合重要风险、PR 整体状态和必要的人工检查建议；具体代码发现放入行内评论。简单改动保持简短，不为每一项机械扩写章节。
- **代码审查发现**模拟可发布的 PR 行内评论：每条都必须针对审查差异引入或加剧的代码、文档、配置、测试或仓库文件问题，并给出可评论的变更文件和行号；二进制资源问题只按文件定位。缺失更新类问题应锚定到产生该义务的代表变更行；同类跨文件问题可合并，但仍须给出代表位置和统一检查范围。无法合理锚定的事项不得硬塞入行内清单。
- 代码审查发现优先列 **【核心规范】**，再列 **【优化建议】**；复杂问题给出修复方向，不堆砌大段代码。没有发现时明确写“未发现代码阻断项 / 优化建议”，不要用 PR 流程缺口填充清单。
- **重要风险与待确认事项**只记录与本次改动相关且值得开发者知晓的剩余风险：说明可信触发场景、可能影响、已有保护、证据缺口及建议的验证 / 后续动作，标明“待确认 / 建议后续处理 / 已由开发者明确接受”等状态。未获明确确认不得声称风险已接受；不重复统计已列出的代码发现，也不把无关历史问题变成本 PR 的修复义务。没有此类事项时可省略；“未发现阻断项”不等于保证没有风险。
- **PR 整体状态**单独报告 CI、自动验证、开发者人工验证、截图、PR 描述、关联 Issue、分支 / 提交和其它无法锚定到变更行的信息；使用状态而不是问题分级标签，并明确哪些待补充项会影响当前合并建议。
- 总结和数量统计必须区分“代码审查发现”与“PR 整体待处理项”，例如“2 个代码阻断项、1 个代码优化建议、2 个 PR 整体待补充项”，不得合并成同一种问题。
- 给修改建议代码时提醒：直接套用 AI 建议可能导致 Workflow 失败，推荐本地参考修改并测试。
- 审查力度保持克制：后端优化建议仅在明显架构违规、重大性能隐患或高价值最佳实践时提出；`website/` 空格、基础校对等琐碎问题交由 Workflow，不必评论。

## 默认输出：总览评论 + 行内评论

无论审查已有 PR 还是提 PR 前的本地变更，默认直接整理成可供用户确认或提交 review 的总览评论与行内评论草稿，无需用户另外要求。用户明确指定其它输出形式时遵从其要求，但仍保留必要的版本结论、验证依据和风险说明。可发布正文须保留对应结论的实际检查依据、是否实测及关键限制；这些是给 PR 作者的证据，不是仅留给审查者的内部备注。

按以下形式输出，方便逐条确认和复制：

1. **总览评论草稿**：在单独的 `markdown` 代码块中提供完整、面向 PR 作者的正文。简述目标与范围、整体判断和实际验证情况，始终包含 API 与配置 / Chart 两项版本结论；需要时加入重要残余风险、PR 整体待补充项及具体人工检查建议。不重复粘贴每条行内问题，也不得出现“建议审查者选择 `Request changes`”等面向审查者的操作指令。
2. **行内评论草稿**：每条对应一个代码审查发现，先在代码块外标明等级、目标文件、diff 行号及必要的左右侧信息，再用独立的 `markdown` 代码块给出实际评论正文。正文面向 PR 作者，说明触发条件、问题、影响、建议动作与验证依据；二进制资源注明文件级评论，不编造行号。没有合适的发现时明确写“无行内评论”，不得用 PR 流程项凑数。尚未创建 PR 时用本地审查快照的路径和行号，明确提交前须按最终 PR diff 重新核对位置。

若有只面向 Skill 使用者的建议，例如采用 `Approve`、`Comment` 或 `Request changes`、评论发布策略或需要审查者决策的事项，在草稿外单列简短的 **“给审查者的建议（不发布）”**；没有则省略。文件定位元数据、严重度统计与审查操作建议不得混入可复制的评论正文。版本与验证结论属于总览必需信息，即使没有变化也要保留；其它只表示“已满足 / 无需行动”且无助 PR 作者的信息无需重复发布。

生成草稿不等于发布评论。只有用户明确授权提交 review 后才可发布；发布前确保用户已确认总览正文、每条行内评论及采用的 GitHub review 操作，并核对当前 PR head / diff 是否仍对应审查快照。若位置或相关代码已变化，先重新核对受影响结论，不向过期行号直接发布。

## 人工检查建议

审查结束时，结合 diff 告诉开发者还需要亲自检查什么，而不是只说“请测试”：

- UI / 前端改动：列出应打开的页面、角色、入口、关键操作和通常应截图的状态；如果改了复用组件、hook、表单控件或 `ui-custom/`，指出可能被牵连的其它页面或流程，要求开发者抽查代表性页面。
- 后端 / CLI 改动：列出建议运行的命令、API 场景、输入输出、权限身份或错误分支；实际执行截图能帮助审查时建议添加，例如 CLI 输出。
- 文档改动：列出需要人工阅读的文档、语言版本、链接、术语、示例命令、Chart 版本占位或关键步骤；提醒开发者 AI 生成文档不能直接提交，必须人工阅读判断。
- Chart / 配置改动：列出需要核对的 values、README、版本号、tag、模板渲染或敏感配置项。
- API / 配置变更触发版本提升时，人工检查建议必须与“版本与部署影响”对应，覆盖实际发布物和升级路径，不能只写泛化的“运行测试”。
- 提交前检查 `git status` / diff，确认没有把用于记录任务、测试、issue 编号、临时方案或开发过程的 task note / 临时文件纳入提交；除非维护者明确要求，这类文件不应提交。
- PR 前要求开发者查看最终文件清单、关键 diff 和 PR 描述；若审查发现需要修改的问题，先迭代处理，再生成或更新 PR 描述。

## PR 描述生成

根 `CONTRIBUTING.md`「Open And Iterate On A Pull Request / 创建并迭代 Pull Request」定义 PR 描述必须包含的信息；**具体生成流程、模板、AI / 开发者测试分组与拒绝条件以 `crater-devel-shared` 的「PR 描述」为准**。

生成 PR 描述前，必须询问开发者亲自做过哪些人工检查，并要求其提供具体页面操作、命令场景或文档阅读检查。若用户尚未说明关联 issue，必须询问是否有关联 issue；有则按 GitHub 可识别格式写入（如 `Resolve #123`），没有则省略。文档改动必须要求开发者说明已阅读检查的文档、语言版本、链接、术语、示例命令、版本占位或关键步骤，并确认是否需要调整。Agent 可以加入自己实际执行过的验证，但必须标注为 AI 执行；如果开发者不提供亲自检查结果，或文档改动没有开发者阅读检查结果，拒绝创建 PR 描述。

生成 PR 描述时保留 review 中的版本决策；发生变化时同时保留发布 / 部署影响和已确认的人工检查结果，不要把它降格为普通实现细节。

若需要创建或更新 PR，必须先把最终 PR 描述展示给开发者并取得确认；不能把开发者没看过的 AI 生成文本直接用于 PR。

## PR 后续迭代

创建 PR 后提醒开发者检查 workflow 状态；如工具可用，可帮助读取 workflow 状态和 PR 链接。若 workflow 失败，先读取失败 job / log，判断根因与是否和本 PR 相关，再给开发者修复方案。处理 Copilot review 或人工 review 时，先读取意见并判断其是否正确、是否值得修改，再给开发者修改方案。未经开发者讨论和确认，不要直接按 workflow / review 意见修改代码。
